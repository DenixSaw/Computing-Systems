# Ручная проверка приложения на этом ПК (16 логических ядер)

## Context
Приложение собрано и проверено автотестами. Теперь нужно руками прогнать его в окнах и
убедиться, что поведение соответствует ТЗ. Пользователь запускает всё сам. Ниже по каждому
сценарию: что выставить, где и что должно получиться. Код не меняется.

Запуск каждого экземпляра — в отдельном терминале из `D:\labpar`:
```
.venv\Scripts\python.exe main.py
```

---

## Сценарий 1. Точность: только master, тестовая функция
**Окно Master** (одна копия, «Запустить как Master»):
- Функция: **Тестовая**. Область подставится сама: x 0…3.141593, y 0…1.570796, z 0…1.
- N = **100**, Деление: любое, Процессов master: 16 (по умолчанию).
- «▶ Запустить расчёт».

**Ожидаем:**
- Интеграл **3.43656367687065**.
- Погрешность: точное **3.4365636569178** (= 2(e−1)), абсолютная **≈1.995e-08**,
  относительная **≈5.806e-09**.
- Время — доли секунды. В таблице итогов 1 узел, master, доля 100 %, слои 0–100.
- Повтор с N = **200**: относительная погрешность примерно в **16 раз меньше** (~3.6e-10),
  потому что у Симпсона ошибка ~h⁴.
- В журнале: «Запуск №… сохранён», пути к `runs\series_test_N100_cores\...`, плюс сообщение,
  что ускорение пока не построено (или построено, если запуск на одном узле уже есть).

## Сценарий 2. Автопоиск и подключение slave
**Master:** открыт, как в сценарии 1 (код группы `lab`, TCP 5000, UDP 5001).
**Окно Slave** (вторая копия, «Запустить как Slave»): поле «Процессов для расчёта» = **4**
(ставить ДО подключения, после подключения поле заблокировано). Галочка автоподключения включена.

Если slave уже подключился с 16 процессами: «Отключиться», поменять на 4, нажать «🔍 Найти master».

**Ожидаем:**
- В списке slave **одна** строка: DESKTOP-1MV05GF, IP **192.168.1.125**, порт 5000.
  Slave подключается автоматически. Статус: «подключён к «DESKTOP-1MV05GF» … ожидание задачи».
- В таблице «Узлы» master появляется строка `DESKTOP-1MV05GF-xxxx`, IP 192.168.1.125, ядра 4,
  статус «подключён».
- В журнале master: «получен запрос DISCOVER…», «отправлен ANNOUNCE…», «Узел … зарегистрирован, ядер: 4».

## Сценарий 3. Серия замеров 1 → 2 → 3 → 4 узла (главный)
Все копии на одном ПК, ядра поровну: **master 4 процесса, каждый slave 4 процесса**.

**Master:** Функция **Тяжёлая** (область 0…2 по всем осям), N = **800**, Деление **По числу ядер**,
Процессов master = **4**. Серия заполнится сама: **heavy_N800_cores**, её не трогать.

Порядок (slave подключать по сценарию 2, у каждого 4 процесса):
1. 0 slave → «Запустить» → T(1).
2. 1 slave → «Запустить» → T(2).
3. 2 slave → «Запустить» → T(3).
4. 3 slave → «Запустить» → T(4).

**Ожидаем:**
- **Интеграл одинаковый во всех четырёх запусках** (≈ 1.47438843…, совпадают ~13 и более знаков).
  Это главная проверка корректности деления.
- Доли примерно равные: 2 узла по ~50 %, 4 узла по ~25 %. Слои идут подряд без пропусков:
  0–399 / 400–800 и т.п. Последний узел получает на 1 слой больше.
- Время (ориентировочно, ~70 нс/точку на ядро): T(1) ≈ 8–15 с, T(2) ≈ T(1)/2,
  T(4) ≈ T(1)/2.5…T(1)/3.5. Ниже идеала, потому что 16 логических ядер — это гипертрединг,
  а не 16 физических. Времена узлов в таблице итогов близки между собой.
- После 1-го запуска в журнале будет «Ускорение … не построены … нет запуска на одном узле»
  только если первым запуском был не одиночный. При порядке выше ускорение строится уже со 2-го.
- «Открыть папку с результатами» → `runs\series_heavy_N800_cores\`: `time_vs_nodes.png`
  (4 точки, время падает), `speedup_vs_nodes.png` (линия ниже пунктира S = n),
  `efficiency_vs_nodes.png` (E < 1 и падает), `summary.csv` (4 строки), `run_<id>\nodes_time.png`
  (столбцы почти равной высоты, master оранжевый).
- Повторить любой запуск (например, с 2 узлами) → в `runs.csv` добавится строка, а на графиках
  точка для 2 узлов **заменится**, а не задвоится.

## Сценарий 4. Баланс: «по ядрам» против «равномерно»
**Master:** процессов **12**; **один** slave с **4** процессами. Тяжёлая, N = **800**.
1. Деление **По числу ядер** → доли ~75 % / ~25 %, времена узлов примерно равны.
2. Деление **Равномерно** (серия сама сменится на `heavy_N800_equal`) → доли 50 / 50,
   **время slave примерно в 3 раза больше, чем у master**, общее время больше, чем в п.1.
   На `nodes_time.png` разница высот хорошо видна.

## Сценарий 5. Остановка
**Master:** Тяжёлая, N = **1600** (долго), 1–2 slave. Запустить, через 3–5 с нажать «■ Остановить».

**Ожидаем:** интеграл «остановлено», статусы «остановлен», в журнале slave «Master остановил
расчёт…» и «Задача отменена». В `runs.csv` строка со `status = stopped`. Новый запуск сразу
после этого работает нормально.

## Сценарий 6. Отказ slave во время расчёта
**Master:** Тяжёлая, N = **1200**, Деление По ядрам, один slave. Запустить и, пока прогресс slave
~20–50 %, **закрыть окно Slave крестиком**.

**Ожидаем:** в журнале master «⚠ Узел … выбыл из расчёта … Master пересчитает его долю сам».
Статус узла «пересчёт на master» → «пересчитано master». Расчёт доходит до конца, **интеграл
совпадает** с обычным запуском при N = 1200. Итог «с пересчётом доли выбывшего узла», в CSV
`status = recovered`, запуск **не попадает** на графики серии.

## Сценарий 7. Код группы и ручное подключение
**Slave:** код группы **`other`** → «🔍 Найти master».
**Ожидаем:** список пуст, оранжевая подсказка «Master не найден: проверьте… UDP-порт 5001,
либо введите IP вручную». В журнале master «код группы не совпадает — запрос проигнорирован».
Затем в «Ручное подключение» ввести IP **127.0.0.1** (или 192.168.1.125), порт **5000** →
«Подключиться» → подключение проходит: TCP группу не проверяет.

## Если что-то пошло не так
- Slave не находит master на этом же ПК: проверить, что коды группы и UDP-порты совпадают,
  или подключиться вручную на 127.0.0.1:5000.
- Брандмауэр Windows при первом запуске master спрашивает разрешение — разрешить для частных сетей.
- Порт 5000 занят (две копии master): в журнале «Не удалось открыть TCP-порт» → сменить порт
  и нажать «Применить и перезапустить сервер».
